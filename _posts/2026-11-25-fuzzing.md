## 들어가며

이 글에서는 퍼징(fuzzing)이 무엇인지, 어떤 종류가 있는지 정리하고, 대표적인 퍼저인 AFL++와 Jackalope를 비교한다. 참고한 자료는 Google의 fuzzing 문서 저장소(google/fuzzing), AFL++ 저장소의 문서, Jackalope 저장소의 README다.

## 퍼징이란

퍼징은 프로그램에 자동으로 만든 입력을 계속 넣어 보면서, 프로그램이 비정상적으로 동작하는 입력을 찾는 테스트 방법이다. 비정상 동작은 보통 크래시(프로그램이 죽는 것)나 행(hang, 프로그램이 멈추거나 끝나지 않는 것)을 말한다.

예를 들어 PNG 이미지를 읽는 프로그램이 있다고 하자. 사람이 직접 테스트하면 정상 PNG 파일 몇 개, 일부러 망가뜨린 파일 몇 개 정도를 넣어 볼 수 있다. 퍼저는 정상 PNG 파일의 바이트를 조금씩 바꾸거나 잘라 붙여서 수백만 개의 변형 파일을 만들고, 하나씩 프로그램에 넣어 본다. 그중 프로그램을 죽게 만드는 파일이 있으면 저장해 둔다. 개발자는 그 파일로 크래시를 재현하고 원인을 찾는다.

### 왜 퍼징을 하는가

일반적인 테스트(유닛 테스트, 통합 테스트)는 "이 기능이 요구사항대로 동작하는가"를 확인한다. 개발자가 예상한 입력을 넣고 예상한 결과가 나오는지 본다.

퍼징은 요구사항과 상관없는 오류를 찾는다. 버퍼 오버플로우나 메모리 누수는 어떤 프로그램에서든 오류지만, 개발자가 이런 버그를 잡는 테스트를 직접 쓰는 경우는 드물다. 그리고 이런 버그가 보안 취약점으로 이어지는 경우가 많다. 그래서 퍼징은 일반 테스트를 대신하는 것이 아니라, 일반 테스트를 쓴 다음에 추가로 하는 테스트다.

퍼징이 쓰이는 목적은 크게 세 가지다.

| 목적 | 설명 |
|---|---|
| 보안 | 신뢰할 수 없는 곳(사용자, 네트워크)에서 입력을 받는 프로그램의 취약점 찾기 |
| 정확성 | 같은 일을 하는 두 구현이 같은 결과를 내는지 확인 |
| 안정성 | 복잡한 입력을 많이 처리하는 프로그램(예: 압축 해제 프로그램)이 어떤 입력에도 죽지 않는지 확인 |

### 퍼징으로 찾는 버그

| 분류 | 예시 |
|---|---|
| 메모리 버그 | 버퍼 오버플로우, use-after-free(해제한 메모리를 다시 사용), 초기화하지 않은 메모리 사용, 메모리 누수 |
| 산술 버그 | 0으로 나누기, 정수 오버플로우, 잘못된 비트 시프트 |
| 일반 크래시 | NULL 포인터 역참조, 처리하지 않은 예외 |
| 동시성 버그 | data race(여러 스레드가 같은 데이터를 동시에 건드림), deadlock |
| 자원 사용 버그 | 메모리 고갈, 무한 루프, 무한 재귀로 인한 스택 오버플로우 |
| 논리 버그 | 같은 프로토콜의 두 구현이 다르게 동작, 압축 후 해제한 결과가 원본과 다름 |

메모리 버그는 특히 C/C++ 프로그램에서 자주 나오고, 공격자가 프로그램 흐름을 바꾸는 데 쓸 수 있어서 보안에서 중요하게 본다.

### 퍼징하기 좋은 대상

신뢰할 수 없거나 복잡한 입력을 받는 코드가 좋은 대상이다. 파일 파서(XML, PDF, 폰트), 이미지·영상 코덱, 네트워크 프로토콜, 암호 라이브러리, 압축 라이브러리, 컴파일러와 인터프리터, 정규식 엔진, 데이터베이스, 브라우저, OS 커널 등이 여기에 해당한다.

## 퍼징 용어

이 글 전체에서 계속 나오는 용어를 먼저 정리한다. 특정 퍼저에서만 쓰는 용어는 해당 부분에서 설명한다.

**시드 (Seed) / 코퍼스 (Corpus)**
시드는 퍼징을 시작할 때 사람이 준비해서 넣어 주는 초기 입력이다. 퍼저는 아무것도 없는 상태에서 시작하는 것보다, 정상적인 입력 몇 개를 받아서 그걸 변형하는 편이 훨씬 빨리 프로그램 깊은 곳까지 들어간다. PNG 프로그램을 퍼징한다면 정상 PNG 파일 몇 개가 시드가 된다.

코퍼스는 입력들의 모음이다. 시드에서 시작해서, 퍼징 중에 의미 있는 입력(새로운 코드를 실행시킨 입력)이 계속 추가되므로 시간이 지날수록 커진다. 처음에 넣는 모음을 따로 시드 코퍼스라고 부르기도 한다. AFL++에서는 코퍼스를 큐(queue)라고 부른다.

**퍼즈 타깃 (Fuzz Target)**
퍼저가 입력을 넣는 함수, 즉 퍼징의 진입점이다. 프로그램 전체를 퍼징하는 경우도 있지만, 보통은 입력을 처리하는 함수 하나를 골라서 그 함수만 반복해서 호출한다. libFuzzer에서는 아래와 같은 모양의 함수를 직접 작성한다.

```cpp
extern "C" int LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size) {
  ParsePng(Data, Size);  // 테스트하고 싶은 함수에 입력을 넘긴다
  return 0;
}
```

`Data`는 퍼저가 만든 입력의 바이트, `Size`는 그 길이다. 퍼저는 입력을 바꿔 가며 이 함수를 계속 호출한다. 이렇게 퍼저와 대상 코드를 연결하는 코드를 하네스(harness)라고도 부른다.

**코드 커버리지 (Code Coverage)**
입력 하나를 넣었을 때 프로그램 코드 중 어디가 실행되었는지를 말한다. 커버리지를 세는 단위는 몇 가지가 있다.

- 기본 블록 (Basic Block): 중간에 분기 없이 처음부터 끝까지 한 번에 실행되는 명령어 묶음이다. `if` 문의 참 쪽 코드, 거짓 쪽 코드가 각각 하나의 블록이 된다.
- 엣지 (Edge): 블록에서 블록으로 이동하는 경로다. A 블록 다음에 B 블록이 실행되었다면 A→B 엣지가 실행된 것이다. 같은 블록을 실행해도 어느 블록에서 왔는지가 다르면 다른 엣지가 된다. AFL++는 엣지 단위로 커버리지를 센다.

새로운 엣지를 실행한 입력은 프로그램의 새로운 부분에 들어갔다는 뜻이므로, 퍼저는 이런 입력을 코퍼스에 남겨 두고 계속 변형한다.

**계측 (Instrumentation)**
프로그램에 감시용 코드를 끼워 넣는 것이다. 퍼저는 커버리지를 알기 위해, 각 블록이나 엣지가 실행될 때마다 "여기를 지나갔다"고 기록하는 코드를 대상 프로그램에 넣는다. 언제, 어떻게 넣느냐에 따라 방식이 나뉜다(아래 "커버리지를 얻는 방법"에서 다룬다).

**새니타이저 (Sanitizer)**
프로그램이 실행되는 동안 버그를 감지하는 도구다. 컴파일할 때 검사 코드를 넣는다.

퍼저는 보통 크래시가 나야 버그를 찾았다고 판단한다. 그런데 버퍼를 몇 바이트 넘어서 쓰는 버그는, 넘친 자리에 중요한 데이터가 없으면 크래시 없이 그냥 지나간다. 새니타이저를 켜고 빌드하면 이런 버그가 생기는 순간 프로그램을 바로 멈추고 어디서 무슨 문제가 생겼는지 알려 준다. 퍼저가 입력을 만들어 넣는 역할이라면, 새니타이저는 버그가 생겼는지 감지하는 역할이다.

| 새니타이저 | 감지하는 것 |
|---|---|
| ASan (AddressSanitizer) | 버퍼 오버플로우, use-after-free 같은 메모리 접근 오류 |
| MSan (MemorySanitizer) | 초기화하지 않은 메모리 읽기 |
| UBSan (UndefinedBehaviorSanitizer) | 정의되지 않은 동작(부호 있는 정수 오버플로우 등) |
| LSan (LeakSanitizer) | 메모리 누수 |
| TSan (ThreadSanitizer) | data race |

## 퍼징의 종류

퍼징은 여러 기준으로 나눌 수 있다.

### 입력을 만드는 방식: 변이 기반과 생성 기반

**변이 기반 퍼징 (Mutation-based Fuzzing)**
이미 있는 입력(시드)을 조금씩 바꿔서 새 입력을 만든다. 바이트 몇 개를 뒤집거나, 숫자를 더하고 빼거나, 일부를 지우거나 복사하거나, 다른 입력과 섞는다. 시드만 있으면 입력 형식을 몰라도 쓸 수 있어서 가장 널리 쓰인다. 다만 체크섬이 있거나 문법이 엄격한 입력은 무작위로 바꾸면 대부분 초반 검사에서 걸러진다.

이 문제를 줄이려고 사전(dictionary)을 함께 쓰기도 한다. 사전은 대상 프로그램이 의미 있게 받아들이는 단어(토큰) 목록이다. HTTP 파서를 퍼징한다면 `GET`, `POST`, `Content-Length:` 같은 문자열을 넣는다. 바이트를 무작위로 바꾸기만 해서는 `Content-Length:` 같은 긴 문자열을 우연히 만들기 어렵지만, 사전이 있으면 퍼저가 이 토큰을 한 덩어리로 입력에 끼워 넣을 수 있다.

**생성 기반 퍼징 (Generation-based Fuzzing)**
입력 형식에 대한 규칙(문법, 명세)을 바탕으로 입력을 처음부터 만든다. 만든 입력이 형식에 맞기 때문에 초반 검사를 통과해서 프로그램 안쪽까지 들어가기 쉽다. 대신 규칙을 사람이 직접 작성해야 한다.

### 프로그램 내부를 얼마나 보는가: 블랙박스, 그레이박스, 화이트박스

**블랙박스 퍼징 (Black-box Fuzzing)**
프로그램 내부를 전혀 보지 않고 입력만 넣고 결과(크래시 여부)만 본다. 준비가 간단하지만, 어떤 입력이 프로그램의 새로운 부분을 실행했는지 모르기 때문에 깊은 곳의 버그를 찾기 어렵다.

**그레이박스 퍼징 (Grey-box Fuzzing)**
계측으로 커버리지 같은 가벼운 정보만 얻어서 입력을 고르는 데 쓴다. 아래의 커버리지 기반 퍼징이 여기에 해당하고, AFL++, libFuzzer, Jackalope가 모두 이 방식이다. 지금 가장 많이 쓰이는 방식이다.

**화이트박스 퍼징 (White-box Fuzzing)**
프로그램의 코드를 분석해서 특정 경로를 실행하는 입력을 계산해 낸다. 기호 실행(symbolic execution)이 대표적인 기법이다. 예를 들어 `if (x * 3 == 1234567)`라는 조건이 있으면, 무작위로는 맞히기 어려운 `x` 값을 수식을 풀어서 바로 구한다. 정확하지만 큰 프로그램에서는 계산량이 너무 많아진다.

### 커버리지 기반 퍼징 (Coverage-guided Fuzzing)

피드백 기반 퍼징(feedback-based, guided fuzzing)이라고도 한다. 변이 기반 퍼징에 피드백을 더한 방식이다.

1. 코퍼스에서 입력 하나를 고른다.
2. 입력을 변형해서 대상 프로그램에 넣는다.
3. 계측으로 어떤 엣지가 실행되었는지 확인한다.
4. 이전에 본 적 없는 엣지가 실행되었으면 그 입력을 코퍼스에 추가한다. 아니면 버린다.
5. 크래시가 나면 그 입력을 따로 저장한다.
6. 1로 돌아간다.

새로운 코드를 실행한 입력만 남겨서 계속 변형하기 때문에, 시간이 지날수록 프로그램의 더 깊은 곳까지 들어간다. 무작위 퍼징보다 훨씬 효율적이라 현재 대부분의 퍼저가 이 방식을 쓴다. AFL이 이 방식을 널리 알렸다.

### 그 밖의 방식

- 문법 기반 퍼징 (Grammar-based Fuzzing): 입력의 문법을 유지한 채로 변형한다. 자바스크립트 엔진처럼 문법이 복잡한 대상에 쓴다.
- 차등 퍼징 (Differential Fuzzing): 같은 기능을 하는 두 프로그램에 같은 입력을 넣고 결과가 다른지 비교한다.

## 커버리지를 얻는 방법

커버리지 기반 퍼저는 커버리지를 알기 위해 대상 프로그램을 계측해야 한다. 소스 코드가 있느냐에 따라 쓸 수 있는 방법이 달라지고, 이 차이가 퍼저를 비교할 때 가장 중요한 기준이 된다.

| 방법 | 원리 | 소스 필요 | 속도 | 예시 |
|---|---|---|---|---|
| 컴파일 시 계측 | 컴파일러가 빌드할 때 계측 코드를 넣는다 | 필요 | 가장 빠름 | AFL++ (afl-cc), libFuzzer |
| 동적 바이너리 계측 (DBI) | 프로그램이 실행되는 동안 코드에 계측 코드를 끼워 넣는다 | 불필요 | 중간 | AFL++ FRIDA 모드, WinAFL(DynamoRIO), Jackalope(TinyInst) |
| 에뮬레이션 | 프로그램을 에뮬레이터 위에서 실행하면서, 에뮬레이터가 명령어를 처리할 때 커버리지를 기록한다 | 불필요 | 느림. 대신 다른 아키텍처 바이너리도 실행 가능 | AFL++ QEMU 모드, unicorn 모드 |
소스 코드가 있으면 컴파일 시 계측을 쓰는 것이 가장 빠르고 정확하다. 상용 프로그램이나 펌웨어처럼 바이너리만 있는 경우에는 나머지 방법을 쓴다. AFL++ 문서에 따르면 QEMU 모드와 FRIDA 모드는 컴파일 시 계측보다 2~5배 정도 느리다.

## 퍼저 살펴보기

### libFuzzer

LLVM(clang 컴파일러) 프로젝트에 포함된 퍼저다. 위의 `LLVMFuzzerTestOneInput` 함수 하나만 작성하면 되고, 유닛 테스트를 쓰는 것과 비슷한 방식이라 처음 퍼징을 해 보는 개발자에게 권장된다. 컴파일 시 계측을 쓰고, 프로세스 하나 안에서 퍼즈 타깃을 반복 호출하는 방식(in-process)이라 빠르다. 소스 코드가 있어야 한다.

### AFL++

#### AFL과 AFL++

AFL(American Fuzzy Lop)은 Michal Zalewski가 만든 커버리지 기반 퍼저다. 사용하기 쉽고 실제로 많은 버그를 찾아서 커버리지 기반 퍼징을 널리 알린 도구다. AFL이 공개된 뒤 여러 연구자가 AFL을 고쳐서 새 기법을 시험했고, 그 결과 AFLFast, Redqueen 같은 수많은 변형이 나왔다. 하지만 원래 AFL은 업데이트가 거의 멈췄다.

AFL++는 AFL의 포크(fork, 원본 코드를 가져와 따로 개발하는 프로젝트)로, 이렇게 흩어진 개선 사항을 하나로 합쳐서 관리하는 프로젝트다. AFL++ 논문 제목도 "AFL++: Combining Incremental Steps of Fuzzing Research"(WOOT 2020)로, 퍼징 연구의 개선 사항을 합쳤다는 뜻이다. 현재 AFL 계열에서 가장 많이 쓰이는 퍼저다.

#### 동작 과정

AFL++ 문서는 퍼저의 동작을 다음과 같이 설명한다.

1. 사용자가 준 시드를 큐에 넣는다.
2. 큐에서 다음 입력을 꺼낸다.
3. 프로그램의 동작(커버리지)이 바뀌지 않는 선에서 입력을 가장 작게 줄인다(trim).
4. 여러 변이 전략으로 입력을 반복해서 변형한다.
5. 변형한 입력이 새로운 상태 변화(새 엣지)를 일으키면 큐에 추가한다.
6. 2로 돌아간다.

3단계처럼 입력의 크기를 줄이는 작업을 최소화(minimization)라고 한다. 커버리지에 영향을 주지 않는 부분을 잘라 내면 입력이 작아져서 실행이 빨라지고, 변이도 의미 있는 부분에 집중된다. 크래시를 일으킨 입력을 최소화하면 크래시와 상관없는 부분이 빠져서 원인을 찾기도 쉬워진다.

이 과정에서 더 넓은 커버리지를 가진 입력이 생기면, 그 입력에 포함되는 예전 입력은 정리한다. 결과적으로 퍼징이 끝나면 크래시와 함께 "작지만 다양한 코드를 실행하는 입력 모음"이 남는다.

#### 주요 기능

AFL++가 원래 AFL보다 나아진 점 중 대표적인 기능은 아래와 같다.

**파워 스케줄 (Power Schedule)**
큐에 있는 입력 중 어떤 입력을 얼마나 많이 변형할지 정하는 방법이다. 모든 입력을 똑같이 변형하는 대신, 드문 경로를 실행하는 입력에 더 많은 시간을 쓴다. AFLFast에서 가져온 기능이다.

**CmpLog (Redqueen)**
비교문을 통과하기 위한 기능이다. 프로그램에 `if (magic == 0xDEADBEEF)` 같은 조건이 있으면, 바이트를 무작위로 바꿔서 4바이트 값을 정확히 맞힐 확률은 약 43억분의 1이다. CmpLog는 프로그램이 실행될 때 비교문의 양쪽 값을 기록해 두고, 입력에서 그 값이 들어간 자리를 찾아 비교 대상 값(`0xDEADBEEF`)으로 바꿔 넣는다. Redqueen 논문의 기법을 AFL++에 맞게 구현한 것이다.

**퍼시스턴트 모드 (Persistent Mode)**
퍼저는 입력 하나마다 대상 프로그램을 실행해야 하는데, 프로그램을 매번 처음부터 실행하면 로딩과 초기화에 시간이 많이 든다. AFL 계열 퍼저는 기본적으로 포크 서버(fork server)를 쓴다. 프로그램을 한 번 실행해서 초기화가 끝난 지점에서 멈춰 두고, 입력이 올 때마다 그 상태를 `fork()`로 복제해서 실행하는 방식이다.

퍼시스턴트 모드는 여기서 더 나아가, 프로세스를 새로 만들지 않고 프로세스 하나 안에서 퍼즈 타깃 함수를 반복문으로 계속 호출한다. 프로세스 생성 비용이 없어서 포크 서버보다 훨씬 빠르다. 대신 대상 함수가 호출 사이에 상태를 남기거나(전역 변수를 바꾸는 등), 메모리를 누수하거나, 중간에 `exit()`를 호출하면 결과가 틀어진다.

**공유 메모리 입력 전달**
퍼저가 만든 입력을 파일로 쓰지 않고, 퍼저와 대상 프로그램이 같이 보는 메모리 영역에 바로 넣어 주는 방식이다. 디스크에 파일을 쓰고 읽는 시간이 줄어든다.

#### 소스 코드가 없는 대상

AFL++는 바이너리만 있는 대상을 위한 모드도 제공한다. 대표적인 것은 두 가지다.

| 모드 | 방식 | 특징 |
|---|---|---|
| QEMU 모드 (`-Q`) | 에뮬레이션 | 가장 기본적인 방법. Linux 전용. 다른 아키텍처 바이너리도 가능 |
| FRIDA 모드 (`-O`) | 동적 바이너리 계측 | 보통 QEMU보다 약간 빠름. macOS(Intel, Apple Silicon)도 지원 |

이 밖에 펌웨어처럼 Linux가 아닌 대상을 위한 unicorn 모드 등도 있다.

### Jackalope

#### 무엇인가

Jackalope는 Google Project Zero의 Ivan Fratric이 만든 커버리지 기반 퍼저로, 소스 코드 없이 바이너리만 있는 대상을 퍼징하는 데 초점을 둔다. 같은 사람이 Windows용 AFL 변형인 WinAFL도 만들었다.

README에 따르면 Jackalope를 만든 이유는 두 가지다. 소스 코드가 있는 대상을 위한 퍼저는 많지만, 바이너리만 있는 대상, 특히 Windows와 macOS를 지원하는 퍼저는 적다. 그리고 있는 퍼저도 코드를 고쳐서 확장하기가 어렵다. 그래서 Jackalope는 다음 두 가지를 목표로 한다.

- 사용자가 변이 방법, 입력 전달 방법, 계측 방법을 쉽게 바꿀 수 있을 것
- 한 컴퓨터에서도, 여러 컴퓨터에 걸쳐서도 쉽게 병렬로 돌릴 수 있을 것

지원하는 OS는 Windows, macOS, Linux, Android다.

#### TinyInst

Jackalope는 계측에 TinyInst를 쓴다. TinyInst는 같은 Project Zero에서 만든 가벼운 동적 바이너리 계측 라이브러리다.

DynamoRIO나 PIN 같은 기존 DBI 프레임워크는 프로세스 전체를 자기 통제 아래에서 실행한다. TinyInst는 사용자가 지정한 모듈(실행 파일이나 라이브러리 하나)만 계측하고, 나머지는 원래 속도로 실행한다. 예를 들어 이미지 라이브러리만 계측하고 운영체제 라이브러리는 그대로 둔다. 그래서 프로세스 시작이 빠르고, 대상 프로세스가 계측하지 않는 모듈에서 많은 시간을 보내는 경우 다른 방법보다 빠를 수 있다. TinyInst 문서에 따르면 커버리지를 수집할 때 성능 저하는 약 20%였다.

대신 대상이 "얌전하다"고 가정한다. 실행 중에 자기 코드를 고치거나, 스택의 리턴 주소를 직접 읽거나 하는 프로그램에는 맞지 않는다. 그래서 악성코드 분석 같은 용도에는 DynamoRIO가 더 적합하다.

#### 구조와 확장

Jackalope는 변이, 입력 전달, 계측 같은 기능이 각각 부품처럼 나뉘어 있어서, 사용자가 필요한 부품만 직접 만들어 바꿔 끼울 수 있다. 예를 들어 입력을 대상에 넘기기 직전에 체크섬을 고쳐 주는 부품을 넣으면, 변이 기반 퍼징에서 체크섬 때문에 입력이 초반에 걸러지는 문제를 해결할 수 있다.

변이는 바이너리 형식용 기본 뮤테이터와 문법 기반 변이 엔진을 제공한다. README에서는 고급 변이 전략은 포함하지 않았다고 밝히고, 대상에 맞는 뮤테이터를 직접 작성하라고 권한다.

병렬 실행은 한 컴퓨터에서는 여러 스레드로 돌리고, 여러 컴퓨터에서는 한 대를 서버로 두고 나머지가 접속하는 방식으로 한다. 서버가 각 퍼저가 찾은 입력, 크래시, 커버리지를 모아서 다시 나눠 준다.

#### 새니타이저 대신

바이너리만 있는 대상에는 컴파일 시 새니타이저를 넣을 수 없다. README에서는 대신 운영체제가 제공하는 메모리 검사 기능을 쓰라고 권한다. Windows에서는 Page Heap, macOS에서는 Guard Malloc이나 MTE(메모리 태깅, 지원하는 Apple 칩에서)를 쓴다.

## AFL++와 Jackalope 비교

두 퍼저는 모두 커버리지 기반 퍼저이고, 퍼시스턴트 모드와 공유 메모리 전달을 지원한다. 차이는 아래와 같다.

| 구분 | AFL++ | Jackalope |
|---|---|---|
| 만든 곳 | AFL 커뮤니티 포크 | Google Project Zero |
| 주된 대상 | 소스 코드가 있는 프로그램 (바이너리 모드도 지원) | 소스 코드가 없는 바이너리 |
| 커버리지 수집 | 컴파일 시 계측이 기본. 바이너리는 QEMU, FRIDA 모드 | TinyInst 동적 계측 |
| 지원 OS | Linux 중심. FRIDA 모드는 macOS 지원 | Windows, macOS, Linux, Android |
| 변이 전략 | 다양함 (파워 스케줄, CmpLog 등) | 기본 뮤테이터 + 문법 기반. 고급 전략은 사용자가 작성 |
| 새니타이저 | ASan 등 컴파일 시 새니타이저 사용 가능 | OS 기능(Page Heap, Guard Malloc) 사용 권장 |
| 병렬 실행 | 여러 인스턴스가 코퍼스 공유 | 스레드 병렬, 서버-클라이언트 분산 |

정리하면 AFL++는 소스 코드가 있는 대상에서 빠르고 강력한 변이 전략을 쓸 수 있는 종합형 퍼저다. 바이너리만 있는 경우를 위한 모드도 갖추고 있지만 대부분 Linux 중심이다. Jackalope는 Windows와 macOS의 바이너리를 퍼징하는 데 초점을 두고, 대상에 맞게 부품을 바꿔 끼울 수 있게 만든 퍼저다. 기본 변이 전략은 단순한 대신 확장하기 쉽다.
