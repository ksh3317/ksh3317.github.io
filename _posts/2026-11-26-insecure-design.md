## 들어가며

OWASP(Open Worldwide Application Security Project)는 웹 애플리케이션 보안을 다루는 비영리 단체다. OWASP Top 10은 이 단체가 몇 년마다 발표하는 웹 애플리케이션 보안 위험 10가지 목록이다. 2025년판에서 여섯 번째 항목이 A06 Insecure Design(안전하지 않은 설계)이다.

이 글에서는 Insecure Design이 무엇인지, 다른 보안 문제와 어떻게 다른지 정리하고, 이를 막는 방법으로 threat modeling을 소개한다. OWASP 공식 페이지, NIST의 개발자 검증 가이드라인(NISTIR 8397), Robert Hurlbut의 threat modeling 워크숍 자료, CWE 항목 3개를 참고했다.

## Insecure Design이란

### 구현 결함과 설계 결함

소프트웨어의 보안 결함은 생긴 단계에 따라 두 가지로 나눌 수 있다.

| 구분 | 구현 결함 (Bug) | 설계 결함 (Flaw) |
|---|---|---|
| 생기는 단계 | 코드를 작성할 때 | 무엇을 어떻게 만들지 정할 때 |
| 원인 | 설계는 맞는데 코드를 잘못 짬 | 필요한 보안 장치를 처음부터 계획하지 않음 |
| 예시 | 입력값 검증을 빠뜨려 SQL Injection이 생김 | 비밀번호 찾기를 "질문과 답변" 방식으로 만듦 |
| 고치는 방법 | 해당 코드를 수정 | 설계를 다시 해야 함 |

Insecure Design은 이 중 설계 결함을 가리킨다. 설계 결함은 코드를 아무리 정확하게 짜도 남아 있다는 점이 구현 결함과 다르다. 예를 들어 비밀번호 찾기 질문이 "어머니의 성함은?"이라면, 이 기능을 버그 없이 구현해도 답을 아는 다른 사람이 계정을 가져갈 수 있다. 문제는 코드가 아니라 "질문 하나로 본인을 확인한다"는 결정에 있다.

### 왜 따로 분류하는가

Insecure Design은 2021년판에서 A04로 처음 추가됐고 2025년판에서는 A06에 있다.

따로 분류하는 이유는 찾는 방법과 고치는 방법이 다르기 때문이다. 정적 분석 도구나 [퍼징](/posts/fuzzing/) 같은 자동화된 검사는 코드에 있는 구현 결함을 찾는 데 강하다. 반면 설계 결함은 코드가 의도대로 동작하는 상태에서 생기기 때문에 이런 도구로는 잘 드러나지 않는다. 결제 단계를 건너뛸 수 있는 쇼핑몰은 크래시도 나지 않고 오류 로그도 남기지 않는다.

고치는 비용도 다르다. 구현 결함은 해당 코드를 고치면 되지만, 설계 결함은 이미 만들어진 구조를 바꿔야 하는 경우가 많다. 그래서 설계 결함은 만들기 전에 찾는 것이 가장 좋다.

## 사례

아래 제목의 번호는 CWE(Common Weakness Enumeration) 번호다. CWE는 MITRE가 관리하는 소프트웨어 약점 목록으로, 약점마다 번호가 붙어 있다.

### CWE-602: 서버에서 할 보안 검사를 클라이언트에서만 함

온라인 쇼핑몰에서 상품 가격을 브라우저의 자바스크립트로 계산하고, 서버는 브라우저가 보낸 가격을 그대로 결제한다고 하자. 사용자는 브라우저 개발자 도구나 프록시 도구로 요청을 가로채서 가격을 1원으로 바꿔 보낼 수 있다.

자바스크립트 코드에 버그가 없어도 이 문제는 생긴다. 사용자가 마음대로 바꿀 수 있는 곳(브라우저)에 보안 검사를 맡긴 설계가 원인이다. 가격 계산과 검증은 서버에서 해야 한다.

### CWE-841: 정해진 순서를 강제하지 않음

쇼핑몰의 주문 과정이 "장바구니 → 결제 → 주문 완료" 순서라고 하자. 각 단계가 별도의 주소(URL)로 되어 있고, 서버가 앞 단계를 거쳤는지 확인하지 않는다면 사용자는 결제 페이지를 건너뛰고 주문 완료 주소로 바로 요청을 보낼 수 있다.

각 페이지는 따로 보면 정상적으로 동작한다. 단계 사이의 순서를 서버가 관리해야 한다는 점을 설계할 때 정하지 않은 것이 문제다.

### CWE-501: 신뢰 경계 위반

신뢰 경계(trust boundary)는 믿을 수 있는 영역과 믿을 수 없는 영역을 나누는 선이다. 서버 내부의 데이터는 믿을 수 있지만, 사용자가 보낸 데이터는 검증하기 전까지 믿을 수 없다.

CWE-501은 이 둘을 같은 곳에 섞어 두는 문제다. 예를 들어 서버가 로그인한 사용자 정보를 세션에 저장하는데, 같은 세션에 사용자가 입력한 값도 검증 없이 저장한다고 하자. 나중에 다른 코드가 세션의 값을 모두 "서버가 확인한 값"으로 여기고 쓰면, 사용자가 넣은 값이 검증된 값처럼 쓰이게 된다. 어떤 데이터를 어디까지 믿을지 설계 단계에서 나누지 않아서 생기는 문제다.

## 예방 방법

### 개발자 검증 최소 기준 (NIST)

NIST(미국 국립표준기술연구소)는 2021년 "Guidelines on Minimum Standards for Developer Verification of Software"(NISTIR 8397)를 발표했다. 같은 해 미국 정부의 사이버보안 행정명령(EO 14028)에 따라 만든 문서로, 개발자가 소프트웨어를 배포하기 전에 최소한 해야 하는 검증 기법 11가지를 권장한다.

| 순서 | 기법 | 설명 |
|---|---|---|
| 1 | Threat Modeling | 어떤 공격이 가능한지 미리 분석 |
| 2 | 자동화 테스트 | 테스트를 자동으로 반복 실행 |
| 3 | 정적 분석 | 코드를 실행하지 않고 취약점 패턴 검사 |
| 4 | 하드코딩된 비밀값 검토 | 코드에 비밀번호, 키가 적혀 있는지 확인 |
| 5 | 내장 보호 기능 사용 | 언어나 운영체제가 제공하는 보호 기능 켜기 |
| 6 | 블랙박스 테스트 | 내부 구조를 모르는 상태에서 기능 테스트 |
| 7 | 코드 구조 기반 테스트 | 코드의 각 부분이 실행되도록 테스트 작성 |
| 8 | 과거 버그 기반 테스트 | 예전에 발견된 버그가 다시 생기지 않는지 확인 |
| 9 | 퍼징 | 무작위로 만든 입력을 대량으로 넣어 오류 찾기 |
| 10 | 웹 앱 스캐너 | 웹 애플리케이션의 알려진 취약점 자동 검사 |
| 11 | 포함된 소프트웨어 점검 | 사용하는 외부 라이브러리의 취약점 확인 |

2번부터 11번은 대부분 이미 작성된 코드를 검사한다. 앞에서 말한 구현 결함을 찾는 기법들이다. 1번 threat modeling만 코드가 아닌 설계를 대상으로 한다. 설계 단계에서 위협을 정리해 두면, 나머지 기법으로 무엇을 테스트해야 하는지도 정할 수 있다.

### Threat Modeling

Threat modeling은 시스템을 이해하고, 그 시스템에 어떤 위협이 있는지 미리 찾아보는 과정이다. 집을 나설 때 문과 창문을 잠그는 것과 비슷하다. 무엇이 잘못될 수 있는지 생각하고, 위험을 따져 보고, 그에 맞게 대비한다.

Robert Hurlbut의 워크숍 자료는 threat modeling을 네 단계로 나눈다.

**1. 시스템 그리기**

먼저 시스템이 어떻게 생겼고 데이터가 어디로 흐르는지 그림으로 그린다. 주로 DFD(Data Flow Diagram, 데이터 흐름도)를 쓴다.

| 요소 | 뜻 | 예시 |
|---|---|---|
| External Entity | 시스템 바깥의 사람이나 시스템 | 사용자, 관리자 |
| Process | 데이터를 처리하는 부분 | 웹 서버, 인증 서비스 |
| Data Store | 데이터를 저장하는 곳 | 데이터베이스, 설정 파일 |
| Data Flow | 데이터가 오가는 경로 | 로그인 요청, 응답 |
| Trust Boundary | 신뢰 수준이 바뀌는 경계 | 인터넷과 내부 서버 사이 |

```text
            ┊ (신뢰 경계)
 [사용자] ──┊── 로그인 요청 ──▶ (웹 서버) ──▶ =회원 DB=
          ◀─┊── 응답 ──────────
            ┊
```

**2. 위협 찾기**

그린 그림을 보면서 "여기서 무엇이 잘못될 수 있나?"를 묻는다. 이때 자주 쓰는 방법이 Microsoft가 만든 STRIDE다. 위협을 6가지로 나누고, 그림의 각 부분에 하나씩 대입해 본다.

| 위협 | 뜻 | 지켜야 할 속성 |
|---|---|---|
| Spoofing | 다른 사람인 척하기 | 인증 |
| Tampering | 데이터 변조 | 무결성 |
| Repudiation | 한 일을 안 했다고 부인 | 부인 방지 |
| Information Disclosure | 정보 유출 | 기밀성 |
| Denial of Service | 서비스 마비 | 가용성 |
| Elevation of Privilege | 권한 상승 | 최소 권한 |

위 그림에 대입하면 이런 질문이 나온다. 로그인 요청이 암호화되지 않은 HTTP로 오가면 중간에서 비밀번호를 볼 수 있지 않나(Information Disclosure)? 다른 사람의 로그인 정보로 접속할 수 있지 않나(Spoofing)? 웹 서버가 죽으면 어떻게 되나(Denial of Service)?

**3. 대응 방안과 우선순위 정하기**

찾은 위협마다 대응 방안을 정한다. 앞의 예에서는 HTTPS 사용, 다중 인증 도입 같은 방안이 나온다. 모든 위협을 한 번에 막을 수는 없으므로 위험도를 매겨 우선순위를 정한다. 워크숍 자료에서는 위험도를 "공격하기 얼마나 쉬운가"와 "성공했을 때 피해가 얼마나 큰가" 두 가지로 판단하고, 각각 높음, 중간, 낮음으로 나눈다.

**4. 후속 조치**

결과를 문서로 남기고, 대응 방안을 새 요구사항이나 수정할 버그로 등록한다. 반영됐는지 확인하고, 시스템에 새 기능이 생기면 다시 검토한다. 한 번 만들고 끝나는 문서가 아니라 시스템과 함께 계속 고쳐 나가는 문서다.

### 언제 해야 하는가

Threat modeling은 개발 과정 중 요구사항과 설계 단계에서 한다. 코드를 짜기 전에 위협을 찾으면 그 결과가 새 요구사항이 되고, 설계에 반영된다. 애자일처럼 짧은 주기로 개발하는 환경에서는 기능을 추가할 때마다 그 기능에 대해서만 짧게 threat modeling을 한다.

## 정리

Insecure Design은 코드를 잘못 짜서 생기는 문제가 아니라, 무엇을 만들지 정하는 단계에서 보안을 고려하지 않아서 생기는 문제다. 그래서 코드를 검사하는 도구로는 잘 잡히지 않고, 만든 뒤에 고치기도 어렵다. 이를 막으려면 설계 단계에서 threat modeling으로 위협을 미리 찾고, 그 결과를 요구사항으로 만들어야 한다. NIST의 개발자 검증 기법 11가지 중 threat modeling만 설계를 대상으로 한다는 점도 이와 같은 맥락이다.
